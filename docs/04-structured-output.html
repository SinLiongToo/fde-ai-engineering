結構化輸出與資料契約Structured output and contracts

只要模型的輸出會被程式讀取，它就是一個 API。這個 API 的另一端是一個機率模型，所以你要用對待外部輸入的方式對待它：先驗證，再使用。

As soon as code reads a model's output, that output is an API, and the other side of that API is a probabilistic model. Treat it the way you treat external input: validate first, then use.

常見誤解Common misconception

「用了 structured output，輸出就保證正確。」它保證的是形狀，不是內容。一個欄位齊全、型別正確、但結論錯誤的 JSON，比一個解析失敗的 JSON 更危險，因為它會安靜地流進下游。

"With structured output, the output is guaranteed correct." It guarantees shape, not content. A JSON object with every field present and typed correctly but a wrong conclusion is more dangerous than one that fails to parse, because it flows silently downstream.

分層防護Defense in layers

第 1 層：provider 的 structured outputLayer 1: provider structured output

主流 API 都提供某種形式的 structured output：你給一份 JSON Schema，模型在產生 token 時就被限制在符合 schema 的範圍內，所以不會再出現「多了一段說明文字」或「括號沒關」的情況。不過各家支援的 schema 關鍵字不同。以 Claude 為例，型別、enum、required 會被強制執行，但數值範圍（minimum/maximum）與字串長度（minLength）不在解碼時強制；官方 SDK 會把這些限制從送出的 schema 移除，改在本機驗證。

Major APIs offer some form of structured output: you supply a JSON Schema and token generation is constrained to it, so "an extra sentence of explanation" or "an unclosed brace" can no longer happen. Supported schema keywords differ by provider, though. On Claude, for example, types, enum and required are enforced, while numeric ranges (minimum/maximum) and string lengths (minLength) are not enforced during decoding; the official SDKs strip them from the schema sent to the API and validate them locally.

結論：不管用哪家 provider，本機的 Pydantic 驗證都不能省。

Conclusion: whatever the provider, local Pydantic validation is not optional.

第 4 層：修復迴圈Layer 4: the repair loop

驗證失敗時，把具體的錯誤訊息當成下一輪的使用者訊息回給模型。三個要點：次數有上限、每次嘗試都記錄（之後分析失敗模式用）、最後失敗時有去處（人工佇列或明確的錯誤），而不是回傳一個預設值。

When validation fails, send the specific error messages back to the model as the next user turn. Three essentials: a cap on attempts, a log entry per attempt (for analysing failure patterns later), and somewhere for final failures to go (a human queue or an explicit error) rather than a silent default.

設計 schema 的建議Schema design tips

  • 能用 enum 就不要用自由文字。下游的 if 判斷需要固定的值。
  • 允許「不知道」。如果資料不足，給模型一個明確的出口（例如 "risk_level": "UNKNOWN" 或可為 null 的欄位），否則它會被迫猜一個答案。
  • 欄位描述寫給模型看。schema 的 description 會影響輸出品質，寫清楚格式與例子。
  • 不要把 confidence 當機率。模型自報的信心分數通常沒有校準。如果需要可靠的信心，用評測資料去校準，或用其他訊號（檢索分數、多次取樣的一致性）。
  • 版本化。schema 改了，下游的解析程式、測試集與儲存的資料都會受影響，當成 API 版本管理。
  • Prefer enums to free text. Downstream if statements need fixed values.
  • Allow "don't know". When information is missing, give the model an explicit exit (e.g. "risk_level": "UNKNOWN" or a nullable field), or it will be forced to guess.
  • Write field descriptions for the model. Schema descriptions affect output quality; state formats and give examples.
  • Don't treat confidence as probability. Self-reported confidence is usually uncalibrated. If you need reliable confidence, calibrate against eval data or use other signals (retrieval scores, agreement across samples).
  • Version it. A schema change affects downstream parsers, test sets and stored data; manage it like an API version.

小測驗Quiz

1. 已經使用 provider 的 structured output，為什麼還需要 Pydantic 驗證？1. You already use provider structured output. Why still validate with Pydantic?
structured output 保證結構，不保證範圍、長度、格式規則，更不會知道「這次檢索到哪些文件」。
Structured output guarantees structure, not ranges, lengths or format rules, and it certainly doesn't know which documents were retrieved this time.
2. 修復迴圈重試 3 次都失敗，最好的處理是？2. The repair loop fails three times. Best handling?
預設值會把失敗偽裝成正常結果，風險評估尤其危險。無限重試會讓成本與延遲失控。
A default disguises failure as a normal result, especially dangerous for risk assessment. Unbounded retries let cost and latency run away.
3. 模型回傳的 JSON 完全通過驗證，但風險等級判斷錯了。這要靠什麼發現？3. The JSON passes every validation, but the risk level is wrong. What catches this?
內容是否正確屬於語意問題，schema 無從判斷。temperature 只影響輸出的變異程度，不保證正確。
Whether content is correct is a semantic question a schema can't answer. Temperature affects variability, not correctness.
