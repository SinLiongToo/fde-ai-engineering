對話記憶與成本Conversation memory and cost

員工問完「特休要提前幾天？」，接著問「那病假呢？」。機器人要記得前一題，才看得懂「那」。但記得越多，每次送出的 token 越多，費用也越高。這一章在兩者之間找平衡。

An employee asks how far ahead to request annual leave, then "what about sick leave?". The bot must remember the previous question to understand "what about". But the more it remembers, the more tokens each request sends and the more it costs. This chapter balances the two.

⏱ 20 分鐘min🧪 bot.py · config.py

這章要加的功能What this chapter adds

  • 對話歷史：只存「問題」與「最終回答」，不存手冊段落。
  • 只把最近幾輪送出去。
  • 記錄每次的 token 用量，換算成費用。
  • Conversation history that stores only questions and final answers, not handbook passages.
  • Sending only the most recent turns.
  • Tracking token usage per request and converting it to cost.

歷史要存什麼What to keep in history

入門篇 B2 說過：API 不會記得你，每次都要把對話重新送出去。但每一輪實際送出的內容，除了問題，還有好幾段手冊（可能是問題的十幾倍長）。如果把這些全部存進歷史，對話越長就越貴，而且舊的手冊段落多半和新問題無關。

Basics chapter B2 showed that the API doesn't remember you, so you resend the conversation each time. But each turn sends not just the question, but several handbook passages, often many times longer. Storing all of that in history makes long chats expensive, and old passages are mostly irrelevant to new questions.

所以我們只存「問題」與「最終回答」。新問題的手冊段落，每次重新搜尋：

取捨Trade-off

只保留最近 4 輪，代表第 5 輪以前的內容機器人會「忘記」。對手冊問答來說通常沒關係，因為大多數問題是獨立的。如果你的場景需要記得很久以前的事（例如長時間的客服對話），常見做法是把舊對話整理成一段摘要放進去。

Keeping only the last 4 turns means the bot "forgets" anything earlier. For handbook Q&A that's usually fine, since most questions are independent. If your use case needs long memory (say, a long support conversation), a common approach is to summarise older turns into a short note.

記錄用量與費用Tracking usage and cost

每次 API 回應都會告訴你這次用了多少輸入與輸出 token。把它記下來，就能算出費用。不要等到月底收到帳單才知道花了多少。

Every API response reports the input and output tokens used. Record them and you can compute cost. Don't wait for the monthly bill to find out what you spent.

注意：一個問題可能呼叫 API 不只一次（用工具時兩次、重試時再多一次），所以「每個問題的成本」要把這些都加起來。chat.py 輸入 /usage 可以看到目前累計。

Note that one question may call the API more than once (twice with a tool, once more on a retry), so cost per question must add them all up. Type /usage in chat.py to see the running total.

保留全部歷史 vs. 只保留最近 4 輪Keep all history vs. keep the last 4 turns

每根柱子是一次請求送出的輸入 token。橘色：保留全部歷史；綠色：只保留最近 4 輪。

Each bar is the input tokens of one request. Orange: keep all history; green: keep the last 4 turns.

保留全部歷史時，每次請求的輸入會一直線性變長，總成本則是越聊越快地增加。只保留最近幾輪，每次的輸入很快就會穩定下來。

Keeping all history makes each request's input grow linearly, so total cost grows faster and faster. Keeping only recent turns makes per-request input level off quickly.

再省一點：prompt cachingSaving more: prompt caching

我們的 system prompt 每次都一模一樣。很多 API 提供 prompt caching：如果 prompt 的開頭和之前的請求完全相同，這段可以用比較便宜的價格計費，也比較快。要用好它只有一個原則：不變的內容放前面，會變的放後面。如果你在 system prompt 開頭放了「現在時間：14:03:22」，每次都不一樣，快取就永遠不會生效。詳細做法見進階篇第 08 章。

Our system prompt is identical every time. Many APIs offer prompt caching: if the beginning of a prompt matches an earlier request exactly, that part is billed at a lower rate and processed faster. One rule makes it work: stable content first, changing content last. Put "current time: 14:03:22" at the top of the system prompt and it differs every time, so the cache never hits. Details in core chapter 08.
