第 2 章Chapter 2

從需求到上線的交付流程The engagement lifecycle

大多數 AI 專案失敗不是因為技術做不到，而是因為一開始沒講清楚要解決什麼、怎樣算成功。這一章談的是在寫程式之前與之後，必須做好的那些事。

Most AI projects fail not because the technology can't do it, but because nobody agreed up front on what problem is being solved and what success means. This chapter covers what has to happen before and after the code.

⏱ 20 分鐘min

讀完這章你能夠After this chapter you can

  • 主持一場需求探索，問出範圍、錯誤代價與決策者。
  • 和客戶一起寫下可量測、有人負責判定的成功條件。
  • 說出每個階段應該交出什麼，以及最常卡住的地方。
  • Run a discovery session that surfaces scope, cost of errors and decision makers.
  • Write measurable success criteria with the customer, each with a named owner.
  • State what each phase must deliver and where projects usually stall.

五個階段Five phases

下圖是本課程使用的階段劃分。實際上各階段會重疊、會來回，時間長短也依專案差異很大，不要把它當成固定的天數表。

The diagram shows the phases this course uses. In practice they overlap and loop, and durations vary widely between projects, so don't treat it as a fixed schedule.

階段 1：釐清問題Phase 1: Discovery

目標是把「我們想用 AI 做 X」變成一段可以驗收的問題描述。最有效的方法是看使用者實際操作，而不是只聽主管描述。

The goal is to turn "we want to use AI for X" into a problem statement that can be accepted or rejected. The most effective method is to watch users do the work, not just listen to their manager describe it.

先確認：這真的需要 LLM 嗎？First check: does this need an LLM at all?

如果輸入格式固定、規則明確，一般的程式或規則引擎更便宜、更快、更好測試。如果是找資料，好的搜尋可能就夠了。LLM 適合的是輸入是自然語言、變化大，而且可以容忍並偵測錯誤的工作。能說出「這部分不需要 AI」，會讓客戶更信任你其他的建議。

If inputs have a fixed format and clear rules, ordinary code or a rules engine is cheaper, faster and easier to test. If the job is finding information, good search may be enough. LLMs fit work where inputs are natural language, highly variable, and errors can be tolerated and detected. Being able to say "this part doesn't need AI" makes the customer trust your other recommendations more.

技巧Tip

把「不能出現的錯誤」和「希望變好的指標」分開寫。權限外洩、對外承諾錯誤價格這類錯誤是零容忍，應該用程式擋，而不是用平均分數衡量。

Separate "errors that must never happen" from "metrics we want to improve". Leaking restricted data or quoting wrong prices externally are zero-tolerance; block them in code rather than averaging them into a score.

階段 2：資料與權限Phase 2: Data and access

  • 第一天就送出存取申請。帳號、VPN、資料庫唯讀帳號、模型 API 的使用核准，都可能要等好幾週。
  • 做一份資料清單：來源、格式、更新頻率、擁有者、誰能看。最後一欄會直接變成檢索的權限過濾條件（第 5 章）。
  • 開始蒐集真實問題。從工單、信件、聊天紀錄中挑出 50 到 100 題，請業務專家寫下正確答案。這就是測試集的雛形（第 7 章）。
  • 確認個資處理方式：哪些欄位要遮蔽、資料能不能送到外部 API、紀錄要保留多久。
  • File access requests on day one. Accounts, VPN, read-only DB users and approval to use a model API can each take weeks.
  • Build a data inventory: source, format, update frequency, owner, who may see it. That last column becomes your retrieval permission filter (chapter 5).
  • Start collecting real questions. Pull 50–100 from tickets, email or chat logs and have domain experts write the correct answers. That is your seed test set (chapter 7).
  • Settle PII handling: which fields to mask, whether data may go to an external API, how long logs are kept.

階段 3：原型Phase 3: Prototype

做一條從輸入到輸出完整打通的細線，而不是把某一層做到完美。用真實資料、交給真實使用者，觀察他們卡在哪裡。這個階段 coding agent 可以大幅加速（第 3 章），但要記得原型的目的是學習，不是交付。

Build a thin slice that runs end to end, rather than perfecting one layer. Use real data, hand it to real users and watch where they get stuck. Coding agents speed this phase up considerably (chapter 3), but remember the prototype exists to learn, not to ship.

注意Watch out

原型 demo 成功後，客戶常會問「下週可以上線嗎？」。事先講清楚原型缺了什麼：評測、監控、權限、錯誤處理。把第 4 階段的工作列成清單給對方看。

After a successful demo, customers often ask "can we go live next week?". Say up front what the prototype lacks: evals, monitoring, permissions, error handling. Show them the phase-4 list.

階段 4：強化Phase 4: Hardening

這是把原型變成正式系統的階段，也是第 4 到 8 章的主要內容：

This turns the prototype into a production system, and is what chapters 4–8 cover:

  • 模型輸出經過 schema 與業務規則驗證（第 4 章）。
  • 檢索有權限過濾，並量過 recall（第 5 章）。
  • 會改資料的操作需要核准，並留下紀錄（第 6 章）。
  • 測試集在每次改動時自動執行，有退步就擋下（第 7 章）。
  • 有追蹤、告警、成本監控與降級方案（第 8 章）。
  • Model output passes schema and business-rule validation (chapter 4).
  • Retrieval filters by permission and has measured recall (chapter 5).
  • Data-changing actions need approval and are logged (chapter 6).
  • The test set runs on every change and blocks regressions (chapter 7).
  • Tracing, alerting, cost monitoring and a degraded mode exist (chapter 8).

階段 5：上線與交接Phase 5: Launch and handover

  • 分階段上線：先讓一小群使用者用，或先「只建議、不執行」，確認指標正常再擴大。
  • 寫 runbook：常見告警代表什麼、怎麼查、怎麼回滾、要找誰。
  • 明確的擁有者：誰負責模型升級？誰維護測試集？誰付 API 費用？
  • 回頭對照成功條件：用第 1 階段寫下的條件做驗收，而不是用感覺。
  • Roll out in stages: start with a small group, or in "suggest, don't act" mode, and widen once metrics hold.
  • Write a runbook: what each alert means, how to investigate, how to roll back, whom to call.
  • Name owners: who handles model upgrades, who maintains the test set, who pays for the API.
  • Review against the success criteria written in phase 1, not against impressions.

範本：架構決策紀錄Template: architecture decision record

重要的技術選擇寫成一頁 ADR。半年後有人問「為什麼不用向量資料庫？」時，你（或接手的人）會感謝現在的自己。

Write important technical choices as one-page ADRs. Six months from now, when someone asks "why didn't we use a vector database?", you or your successor will be glad you did.

小測驗Quiz

1. 哪一條是寫得好的成功條件？1. Which is a well-written success criterion?
好的條件說清楚量什麼、怎麼量、門檻多少、誰判定。另外兩個選項無法驗收。
A good criterion states what, how, the threshold and who decides. The other two can't be accepted or rejected.
2. 專案第一週，最該優先啟動的是？2. In week one, what should you start first?
存取申請等待時間長，越早送越好；真實問題是之後評測與設計的基礎。技術選型可以等你看過資料再決定。
Access requests have long lead times, so file them early; real questions underpin evaluation and design. Technology choices can wait until you've seen the data.
3. 原型 demo 很成功，客戶要求下週上線。你應該？3. The demo went well and the customer wants to go live next week. You should:
直接答應會讓沒有防護的系統面對真實使用者；直接拒絕則浪費了客戶的熱度。分階段上線（例如先開給 10 位使用者、只給建議）兩者兼顧。
Agreeing exposes an unprotected system to real users; refusing wastes the customer's momentum. A staged rollout (say 10 users, suggestion-only) serves both.
