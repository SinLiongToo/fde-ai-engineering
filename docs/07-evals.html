評測：把感覺變成數字Evals: from vibes to numbers

改了 prompt、換了模型、調了切段，系統是變好還是變差？沒有評測，你只能憑感覺回答；而感覺通常來自你剛好試的那三個問題。評測讓「改進」變成可以驗證的主張。

You changed the prompt, the model or the chunking. Is the system better or worse? Without evals you answer by feel, and the feeling usually comes from the three questions you happened to try. Evals turn "improvement" into a claim you can check.

從錯誤分析開始，不是從指標開始Start with error analysis, not metrics

常見的錯誤是一開始就套用現成的指標庫（「faithfulness」「relevance」），然後對著分數調整。比較有效的順序是：

A common mistake is to start by adopting an off-the-shelf metric suite ("faithfulness", "relevance") and tune against those scores. A more effective order:

  1. 看真實的輸出Read real outputs 拿 50 到 100 筆真實的請求與回應（含檢索結果與工具呼叫），一筆一筆讀，記下哪裡不對。 Take 50–100 real requests and responses (with retrieval results and tool calls) and read them one by one, noting what's wrong.
  2. 把問題分類Group the problems 例如：沒找到對的文件、找到但答錯、引用不存在的段落、該拒答卻硬答、格式錯。數一數各類有多少。 For example: right document not retrieved, retrieved but misread, cited a non-existent passage, answered when it should have declined, wrong format. Count each category.
  3. 針對最大的類別寫測試Write tests for the biggest categories 每個案例加上類別標籤。這樣分數退步時，你知道是哪一類壞了。 Tag each case with its category, so when a score drops you know which kind of behaviour broke.
  4. 持續補充Keep adding 每次正式環境出事，修好之後把那個案例加進測試集，讓它不會再發生。 Every production incident, once fixed, becomes a test case so it can't recur unnoticed.

測試集長什麼樣子What a test set looks like

lab 的測試集是一個 JSONL 檔，每行一個案例。注意它包含權限測試（forbidden）與一個已知會失敗的案例：誠實的測試集應該反映系統真正的弱點，而不是全部通過。

The lab's test set is a JSONL file, one case per line. Note it includes permission tests (forbidden) and a case that is known to fail: an honest test set reflects the system's real weaknesses rather than passing everything.

  • 來源：真實流量為主，加上邊界案例與對抗性案例（權限、提示注入）。
  • 大小：從 50 到 100 題開始就有用。重要的是涵蓋各個類別，而不是總數。
  • 標準答案由領域專家確認，不是由模型產生後直接採用。
  • 不要讓測試案例流進 prompt（例如當作 few-shot 範例），否則分數會虛高。
  • Sources: mostly real traffic, plus edge cases and adversarial cases (permissions, prompt injection).
  • Size: 50–100 cases is already useful. Coverage of categories matters more than the total.
  • Reference answers are confirmed by domain experts, not generated by a model and accepted as-is.
  • Keep test cases out of the prompt (e.g. as few-shot examples), or scores will be inflated.

LLM 評審的偏誤LLM-judge biases

  • 位置偏誤：兩兩比較時偏好第一個或第二個。對策：交換順序各評一次。
  • 長度偏誤：偏好比較長的回答。對策：評分標準明確寫出「長度不是優點」，並檢查分數與長度的相關性。
  • 自我偏好：偏好和自己風格相近的輸出。對策：評審模型與被評模型分開，並用人工標註驗證。
  • 模糊的量表：1 到 10 分很難一致。對策：用「通過／不通過」加上一句理由，比分數更穩定也更好除錯。
  • Position bias: in pairwise comparison it favours the first or second answer. Fix: grade both orders.
  • Length bias: it favours longer answers. Fix: say explicitly in the rubric that length is not a virtue, and check score/length correlation.
  • Self-preference: it favours outputs in its own style. Fix: separate judge and subject models, and validate against human labels.
  • Vague scales: 1–10 ratings are hard to keep consistent. Fix: pass/fail plus a one-sentence reason is steadier and easier to debug.
校準評審Calibrating a judge

請領域專家標註 50 到 100 筆「通過／不通過」，再讓 LLM 評審評同一批。分別看兩個數字：專家說不通過的，評審抓到多少（漏掉的會讓壞答案溜過）；評審說不通過的，有多少專家也同意（誤判會讓 CI 一直紅燈）。兩者都夠高之前，不要用評審的分數擋合併。

Have domain experts label 50–100 outputs pass/fail, then run the judge on the same set. Look at two numbers: of the outputs experts failed, how many did the judge catch (misses let bad answers through)? Of those the judge failed, how many did experts agree with (false alarms keep CI red)? Don't gate merges on the judge until both are high enough.

在 CI 中擋下退步Blocking regressions in CI

lab 的評測做三件事：逐題評分並列出失敗原因、依標籤彙總、和存檔的 baseline 比較。權限外洩是零容忍，其餘指標則看「有沒有比 baseline 差」。

The lab's eval does three things: grades each case and lists failure reasons, aggregates by tag, and compares against a stored baseline. Permission leaks are zero-tolerance; other metrics are judged against the baseline.

baseline 怎麼更新Updating the baseline

分數變好時，由人看過結果後執行 --update-baseline，並把 baseline.json 的變更和程式一起提交審查。不要讓 CI 自動更新 baseline，否則退步會被悄悄吸收。

When scores improve, a person reviews the results and runs --update-baseline, committing the baseline.json change for review alongside the code. Never let CI update the baseline automatically, or regressions get quietly absorbed.

樣本數與雜訊Sample size and noise

實務上的對策：

Practical countermeasures:

  • 零容忍的項目用程式擋（權限、格式），不受雜訊影響。
  • 題數少時設容忍度，或改看「哪幾題從通過變失敗」，逐題檢查。
  • 輸出有隨機性時，每題跑多次，看平均或通過比例。
  • 重要決策（換模型、上線）用更大的測試集，例如數百題以上。
  • Block zero-tolerance items in code (permissions, format); they are immune to noise.
  • With few cases, allow a tolerance, or look at which cases flipped from pass to fail and inspect them.
  • For stochastic output, run each case several times and use the average or pass ratio.
  • Use a larger set for big decisions (model switch, launch), e.g. several hundred cases.

上線後的評測Evaluation after launch

離線測試集代表的是過去。上線後還需要：

An offline test set represents the past. After launch you also need:

  • 使用者訊號：讚／倒讚、重新提問、轉人工、複製答案的比例。
  • 抽樣人工審查：每週隨機抽一批正式環境的對話讓專家評分，追蹤趨勢。
  • 線上的程式檢查：每次回應都跑格式、引用、權限檢查，失敗就告警。
  • 把新的失敗加回測試集，形成迴圈。
  • User signals: thumbs up/down, rephrased questions, escalations to a human, copy rate.
  • Sampled human review: each week experts grade a random sample of production conversations; track the trend.
  • Online code checks: run format, citation and permission checks on every response and alert on failures.
  • Feed new failures back into the test set, closing the loop.

現成的工具（例如 Ragas、DeepEval、promptfoo、LangSmith、Braintrust、Arize Phoenix）可以省下建置追蹤與報表的時間，但這些工具的 API 變動很快。先理解本章的概念，工具只是實作方式。

Off-the-shelf tools (Ragas, DeepEval, promptfoo, LangSmith, Braintrust, Arize Phoenix and others) save time on tracing and reporting, but their APIs change quickly. Understand the concepts in this chapter first; the tools are just implementations.
