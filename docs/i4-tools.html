工具呼叫：查個人資料Tool calls: personal data

「我今年還剩幾天特休？」手冊只寫規定，寫不出你個人的餘額。這種問題要查人事系統。這一章讓 AI 可以「請你的程式幫它查」，這個機制叫工具呼叫（tool calling）。

"How many days of annual leave do I have left?" The handbook states rules, not your personal balance; that needs the HR system. This chapter lets the AI ask your code to look things up, a mechanism called tool calling.

⏱ 25 分鐘min🧪 tools.py · bot.py

這章要加的功能What this chapter adds

  • 兩個工具：查特休餘額、查今天日期。
  • 工具迴圈：AI 要用工具 → 你的程式執行 → 結果交回 → AI 繼續回答。
  • 三道防護：輪數上限、錯誤也回給 AI、查誰的資料由登入者決定。
  • Two tools: leave balance and today's date.
  • The tool loop: AI asks for a tool → your code runs it → result goes back → AI continues.
  • Three safeguards: a round limit, errors returned to the AI, and "whose data" decided by the login.

AI 不會自己執行工具The AI doesn't run tools itself

一句話重點Key point

AI 只會說「我想呼叫 get_leave_balance」。真正去查資料的，永遠是你的程式。所以你完全控制它能查什麼、查誰的。

The AI only says "I'd like to call get_leave_balance". Your code is always what actually fetches the data. So you fully control what it can look up, and whose.

定義工具Defining tools

工具就是一份說明：名稱、做什麼、需要哪些參數（用 JSON Schema 描述）。AI 讀這份說明來決定要不要用、怎麼用，所以 description 要寫清楚。

A tool is a description: name, purpose and parameters (as JSON Schema). The AI reads it to decide whether and how to use the tool, so write the description carefully.

最重要的設計決定The most important design decision

get_leave_balance 沒有 employee_id 參數。如果有，使用者只要說「幫我查老闆還剩幾天特休」，AI 就可能乖乖把老闆的編號填進去。查誰的資料，應該由登入系統決定（user_id 由你的程式傳入），而不是由 AI 決定。

get_leave_balance has no employee_id parameter. If it did, a user could say "check my boss's remaining leave" and the AI might dutifully fill in the boss's ID. Whose data is read should be decided by the login system (your code passes user_id), never by the AI.

工具迴圈The tool loop

每次呼叫 API，回應裡的 stop_reason 會告訴你它為什麼停下來。如果是 tool_use，代表它在等工具的結果：

Each API response carries a stop_reason saying why it stopped. tool_use means it's waiting for tool results:

  1. 輪數上限：模型可能一直要求用工具。沒有上限，就是一個會燒錢的無窮迴圈。
  2. 原封不動放回：AI 的回應（包含 tool_use 區塊）要完整加回對話，不要只挑文字。
  3. user_id 來自登入：見上面的說明。
  4. 錯誤也回報：查不到資料時，用 is_error 告訴 AI，讓它可以跟使用者解釋，而不是整個程式當掉。
  5. 同一則訊息：如果 AI 一次要求多個工具，所有結果放在同一則 user 訊息裡回傳，每個結果的 tool_use_id 要對應到原本的請求。
  6. 其他停止原因：max_tokens（被截斷）或 refusal（拒答）時，不要把內容當成正常答案。很多範例只判斷 end_turn，遇到這些情況會出錯。
  1. Round limit: the model may keep asking for tools. Without a cap, that's an infinite loop that burns money.
  2. Append unchanged: add the AI's full response (tool_use blocks included) back to the conversation; don't keep only the text.
  3. user_id from the login: see above.
  4. Report errors: when lookup fails, tell the AI via is_error so it can explain to the user instead of the program crashing.
  5. One message: if the AI requests several tools at once, return all results in a single user message, each tool_use_id matching its request.
  6. Other stop reasons: on max_tokens (truncated) or refusal, don't treat the content as a normal answer. Many examples only check end_turn and break in these cases.

小測驗Quiz



  

    1. 為什麼 get_leave_balance 不接受 employee_id 參數？1. Why doesn't get_leave_balance take an employee_id parameter?
    
    
    
    
AI 會照使用者的話做事，所以權限不能交給它判斷。把權限放在程式碼裡，而不是 prompt 裡。

    
The AI follows what users say, so it can't be trusted with permission decisions. Put permissions in code, not in the prompt.

  

  

    2. 工具迴圈只寫了 while stop_reason != "end_turn"。會有什麼問題？2. A tool loop is written as while stop_reason != "end_turn". What's the problem?
    
    
    
    
正確寫法是「stop_reason 是 tool_use 才繼續」，再加上輪數上限，並另外處理其他停止原因。

    
Continue only while stop_reason is tool_use, add a round limit, and handle the other stop reasons explicitly.
